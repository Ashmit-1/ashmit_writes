01 The Big Picture

Fine-tuning is how we turn a generic, next-token-predicting model into a useful assistant, coder, or domain expert.

A pretrained LLM (like the base version of Llama or Mistral) has read enormous amounts of text and learned language patterns, world knowledge, and reasoning. But it doesn't know how to chat, follow instructions, or align with human preferences. It just continues whatever text you give it.

Fine-tuning is the process of taking that pretrained model and updating its weights on a smaller, curated dataset so it behaves the way you want.

The central intuition

Pretraining teaches the model language. Fine-tuning teaches it behavior.

Think of pretraining as a four-year liberal arts degree. Fine-tuning is the on-the-job training at a specific company. The foundation is already there; you're shaping how it gets applied.

The modern post-training pipeline

Most frontier models today go through three or four stages after the initial pretraining:

Pretraining → Continued pretraining (optional) → Supervised fine-tuning (SFT) → Preference learning (DPO / RLHF / GRPO)

Each stage adds a different kind of capability. We'll unpack them one by one.

02 Why It Matters

Fine-tuning is the bridge between a model that can and a model that does. Without it:

  • A 70B-parameter model would ramble instead of answering your question.
  • It would refuse nothing, or refuse everything, depending on how it was trained.
  • It would have no idea what "format this as JSON" means.
  • It would be unusable in production, no matter how smart it is.

With fine-tuning, the same base model can become a medical assistant, a code reviewer, a customer support agent, or a reasoning engine — all from the same weights, just different training data.

Why this matters now Open-weight models (Llama, Mistral, Qwen, Gemma) plus efficient fine-tuning methods (LoRA, QLoRA) mean a single developer with one GPU can produce a specialized model that rivals much larger general-purpose ones for a narrow task. This is the biggest democratizing shift in AI since GPT-2.

03 Core Concepts: What You're Actually Training

Before fine-tuning anything, you need a working mental model of what's inside the model.

Transformers in 60 seconds

A transformer LLM is, at its core, a stack of identical layers. Each layer has two main components:

  1. Self-attention — lets every token look at every other token and decide what to pay attention to.
  2. Feed-forward network (FFN) — a pair of large weight matrices that transform each token's representation independently.

The entire model is just weights — billions of floating-point numbers arranged in matrices. "Training" means adjusting those weights so the model's predictions get better.

Pretraining vs fine-tuning

Pretraining
  • Objective: predict the next token
  • Data: trillions of tokens from the internet
  • Compute: thousands of GPUs for months
  • Result: a "base" model
Fine-tuning
  • Objective: whatever you want (chat, follow instructions, reason)
  • Data: thousands to millions of curated examples
  • Compute: one to eight GPUs for hours or days
  • Result: a useful model

Continued pretraining

Sometimes you want to add new knowledge or a new language to an existing model without starting over. You continue next-token prediction on a new corpus — this is called continued pretraining. It's still pretraining in objective, but applied to an already-trained model.

Rule of thumb If your goal is "teach the model new facts or a new domain," use continued pretraining. If your goal is "teach the model a new behavior or format," use SFT.

LLMs vs SLMs

LLMs (Large Language Models) are typically 7B+ parameters. SLMs (Small Language Models) are typically 1–3B parameters. The distinction matters for fine-tuning because:

  • SLMs fit on consumer GPUs, even in full precision.
  • SLMs are more prone to overfitting — they have less capacity to generalize.
  • Specialized SLMs (e.g., code models, math models) are often created by distilling a large model's outputs into a small one, then fine-tuning on curated data.

04 Data: The Part Everyone Underestimates

In fine-tuning, data quality matters more than model size, more than hyperparameters, more than anything else.

The three kinds of fine-tuning data

Raw text. Just sequences of tokens. The model learns to predict the next one. Used for pretraining and continued pretraining.

Example: "The capital of France is Paris. The city is known for..."

Instruction-response pairs. Each example has a prompt (instruction) and a completion (response). The model learns to produce the completion given the prompt.

{
  "instruction": "Summarize this email in one sentence.",
  "input": "Hi team, the Q3 review is moved to Friday...",
  "output": "The Q3 review has been rescheduled to Friday."
}

Quality matters enormously: a few thousand clean, diverse examples beat a million noisy ones.

Preference pairs. For the same prompt, you have a chosen (preferred) response and a rejected response. Used for DPO, RLHF, and similar methods.

{
  "prompt": "Explain quantum entanglement simply.",
  "chosen": "Imagine two coins that always land the same way, no matter how far apart...",
  "rejected": "Quantum entanglement is a physical phenomenon that occurs when..."
}

Chat templates

Every model family has its own chat template — a specific format for encoding conversations into tokens. Llama uses <|begin_of_text|><|start_header_id|>user<|end_header_id|>. Mistral uses [INST] ... [/INST]. If you fine-tune with the wrong template, the model will silently produce garbage.

Common mistake Using a generic prompt format instead of the model's native chat template. Always use the tokenizer's apply_chat_template method.

Data quality heuristics

  • Deduplicate. Repeated examples cause memorization.
  • Filter by length. Extremely long or extremely short examples are usually noise.
  • Check for contamination. If your eval set appears in your training data, your metrics are meaningless.
  • Use a model to grade data. A stronger model can score your examples for quality, then you keep the top fraction.
  • Balance domains. If 90% of your data is code, the model will become a code model.

05 Full Fine-Tuning vs PEFT

You have two choices: update every weight, or update a tiny fraction. The second option changed the field.

Full fine-tuning

Update every parameter of the model. This is what was done for GPT-3 → InstructGPT. It works well but is expensive:

  • A 7B model in full precision (FP32) needs ~28 GB just to load the weights.
  • Training adds optimizer states (~2× model size in Adam) and gradients (~1×).
  • Total VRAM for full fine-tuning a 7B model: ~60–80 GB, even with mixed precision.
  • That's a multi-GPU setup for most people.

Parameter-Efficient Fine-Tuning (PEFT)

Instead of updating all weights, you freeze the base model and inject a small set of trainable parameters. The base model stays fixed; only the new parameters learn.

The dominant PEFT method today is LoRA — and its quantized variant, QLoRA.

How LoRA works (the math, gently)

A transformer layer has a weight matrix W of shape d × d. During training, we want to learn an update ΔW. Instead of storing a full d × d matrix, LoRA says:

ΔW = B · A

where B is d × r and A is r × d, and r ≪ d (typically 4–64).

The forward pass becomes: output = W·x + B·A·x. At inference, you can merge W + B·A into a single matrix — no latency cost.

Why this works Empirically, the weight updates during fine-tuning have very low "intrinsic rank" — they live in a low-dimensional subspace. LoRA exploits this. You're not losing much expressivity, but you're saving enormous amounts of memory and compute.

QLoRA: quantize the base, LoRA the rest

QLoRA (Dettmers et al., 2023) combines two ideas:

  1. 4-bit quantization of the base model using NF4 (NormalFloat 4-bit), a data type designed for normally-distributed weights.
  2. LoRA adapters trained in higher precision (typically BF16) on top.

The result: you can fine-tune a 65B model on a single 48 GB GPU. Quality loss is minimal compared to full fine-tuning on most benchmarks.

06 Quantization and Memory

Memory is the binding constraint in fine-tuning. Quantization is how you get more model per GPU.

What quantization does

Each weight is normally stored as a 32-bit or 16-bit floating-point number. Quantization reduces this to 8, 4, or even 2 bits per weight, at the cost of some precision.

Quantization methods at a glance

  • RTN (Round-To-Nearest): simplest, just rounds weights. Fast but lossy.
  • GPTQ: post-training quantization using a calibration dataset. Good for inference.
  • AWQ: protects important weights during quantization. Better quality than GPTQ at similar bit-rates.
  • GGUF (llama.cpp): CPU-friendly quantization, supports mixed precision per layer.
  • NF4 (QLoRA): designed for normally-distributed weights; the standard for 4-bit training.
Practical tip For fine-tuning, use QLoRA with NF4. For inference deployment, AWQ or GGUF are usually better choices. Don't mix them up.

07 The Ecosystem: HF, Unsloth, and Friends

You don't train from scratch. You stand on the shoulders of a mature open-source stack.

Hugging Face stack

  • transformers — model loading, tokenization, inference.
  • datasets — streaming, caching, and processing data.
  • peft — LoRA, AdaLoRA, prefix tuning, and other adapters.
  • trl — SFTTrainer, DPOTrainer, GRPOTrainer, reward modeling, PPO.
  • accelerate — distributed training, mixed precision, device mapping.

Unsloth

Unsloth is a library that rewrites key parts of the training loop in custom CUDA kernels. The result:

  • ~2× faster training
  • ~60% less memory
  • Same numerical output as stock HF

It's become the default choice for most hobbyist and small-team fine-tuning. The API is a drop-in replacement for HF's SFTTrainer.

Other notable tools

  • Axolotl — YAML-config-driven fine-tuning; great for reproducibility.
  • LLaMA-Factory — web UI for fine-tuning, popular in the Chinese open-source community.
  • Open-Instruct — from AI2, a research-grade SFT + DPO pipeline.
  • NeMo-Aligner — NVIDIA's stack for large-scale alignment training.

08 Hyperparameters and Training Strategy

A few knobs matter a lot. Most don't. Here's where to focus.

The ones that matter

  • Learning rate: the single most important hyperparameter. For LoRA on a 7B model, start at 1e-4 to 3e-4. For full fine-tuning, 1e-5 to 5e-5.
  • Number of epochs: for SFT, 1–3 epochs is usually right. More than that risks overfitting.
  • LoRA rank (r): 8–16 for most tasks. 32–64 for complex reasoning or math.
  • LoRA alpha: typically 2× the rank. Controls the scaling of the update.
  • Batch size: effective batch size of 16–64 works well. Use gradient accumulation if your GPU is small.
  • Warmup: 3–10% of total steps, linear warmup.

The ones you can mostly ignore

  • Optimizer: AdamW with β₁=0.9, β₂=0.95, weight decay 0.01 is fine for almost everything.
  • LR scheduler: cosine with min LR at 10% of peak is a safe default.
  • Max sequence length: match your task. 2048 for chat, 4096–8192 for long-form.

Catastrophic forgetting

When you fine-tune on a narrow task, the model can lose general capabilities it had before. This is catastrophic forgetting. Mitigations:

  • Mix in general data. Keep 10–30% of your data as broad conversational or reasoning examples.
  • Use a low learning rate. Smaller updates preserve more of the original knowledge.
  • Use LoRA, not full fine-tuning. The frozen base model retains its knowledge; LoRA only adds new behavior.
  • Replay. Include a small fraction of pretraining data in the fine-tuning mix.

09 Prediction Check

Before we move on, let's see if the concepts are clicking.

🤔 You fine-tune a 7B model on 500 examples of medical Q&A for 10 epochs with a high learning rate. What's most likely to happen?
Answer: B. With a small dataset, high LR, and many epochs, the model will memorize the training data and forget much of what it knew before. This is textbook catastrophic forgetting plus overfitting. Fix: fewer epochs (1–2), lower LR, mix in general data, use LoRA.
🤔 You want to fine-tune a 70B model on a single 48 GB GPU. Which approach is realistic?
Answer: C. A 70B model in BF16 needs ~140 GB just to load. Even LoRA in BF16 needs ~140 GB + optimizer states. Only QLoRA (4-bit base + LoRA adapters) fits in 48 GB — the base model takes ~35 GB, plus adapters and gradients you're around 40–45 GB.

10 Preference Learning: DPO, RLHF, GRPO

SFT teaches the model what good outputs look like. Preference learning teaches it what humans prefer — which is a harder, more subtle signal.

Why SFT isn't enough

After SFT, the model can follow instructions. But it can still:

  • Generate plausible-sounding nonsense (hallucination)
  • Be sycophantic — agree with wrong user premises
  • Refuse safe requests or comply with unsafe ones
  • Lack nuance in tone and style

Preference learning fixes this by training directly on comparisons: "given this prompt, response A is better than response B."

Three approaches, compared

RLHF with PPO

The original approach from InstructGPT (Ouyang et al., 2022). Four models in the loop:

  1. Policy model — the LLM you're training.
  2. Reference model — a frozen copy of the SFT model (prevents drifting too far).
  3. Reward model — a classifier trained on preference data that scores responses.
  4. Critic model — estimates the value of states for the RL algorithm.

The policy generates responses; the reward model scores them; PPO updates the policy to maximize reward while staying close to the reference (via a KL penalty).

Pros: proven at scale, flexible. Cons: complex, unstable, needs 4× the memory, reward hacking is a real risk.

Direct Preference Optimization (DPO)

DPO (Rafailov et al., 2023) showed you can skip the reward model entirely. The key insight: there's a closed-form mapping between a reward function and the optimal policy. Substitute it in, and you get a loss that trains the policy directly on preference pairs:

LDPO = −log σ( β · [log π(yw|x)/πref(yw|x) − log π(yl|x)/πref(yl|x)] )

You only need two models: the policy and a frozen reference. Much simpler, more stable, and usually as good as PPO for chat models.

Pros: simple, stable, no reward model. Cons: limited to offline preference data; can't explore.

GRPO — the reasoning-era algorithm

Group Relative Policy Optimization, from DeepSeek (2024/2025), is a variant of RL designed for reasoning models like DeepSeek-R1.

The key difference: instead of a learned critic, GRPO samples a group of responses for each prompt, scores them with a rule-based reward (e.g., "does the final answer match the ground truth?"), and normalizes within the group.

This is what enables reinforcement learning at scale for math and code — no reward model needed, just verifiable outcomes. It's the algorithm behind the "reasoning" behavior in models like DeepSeek-R1 and is increasingly used for agentic and tool-use training.

Pros: no critic, scales to reasoning, stable. Cons: needs verifiable rewards; not a drop-in for open-ended chat.

Which should you use? For most chat/assistant models: DPO. For reasoning, math, code, or agentic models: GRPO. For research or when you need online data collection: PPO.

11 Evaluation and Benchmarking

You can't improve what you don't measure. But measuring LLMs is harder than it looks.

Three layers of evaluation

  1. Automatic benchmarks: MMLU, HumanEval, GSM8K, MT-Bench, Arena ELO. Fast, cheap, but can be gamed and don't capture real-world quality.
  2. Task-specific metrics: Exact match, F1, BLEU, ROUGE, pass@k for code. Useful when you have a clear ground truth.
  3. Human evaluation: side-by-side comparisons, rubric-based scoring. The gold standard, but slow and expensive.

What to actually do

  • Build a private eval set of 100–500 examples representative of your use case. This is worth more than any public benchmark.
  • Check for regression on general capabilities (chat, reasoning) after fine-tuning.
  • Use LLM-as-judge (e.g., GPT-4 or a strong open model) to score outputs on rubrics. It's imperfect but scales.
  • Watch for contamination — if your eval appears in training data, results are meaningless.
Common misconception "Higher MMLU = better model." MMLU saturates on modern models, is heavily contaminated, and doesn't correlate well with real-world chat quality. Treat public benchmarks as one signal among many.

12 Distillation, Merging, and Deployment

Once you've trained a model, you often want to make it smaller, combine it with others, or ship it.

Distillation

Train a small "student" model to mimic a large "teacher." The student learns from the teacher's soft probability distributions, not just hard labels. This is how most specialized SLMs are built — e.g., Phi, Gemma, and many "mini" models are distilled from much larger ones.

Model merging

You can average the weights of multiple fine-tuned models to get something that combines their strengths. Methods include:

  • Linear merging: simple weighted average of weights.
  • TIES: trims irrelevant changes, then merges.
  • DARE: randomly drops and rescales deltas before merging.

Merging is surprisingly effective and free — you just do math on checkpoint files.

Deployment formats

  • Safetensors + HF Transformers: the default for Python serving.
  • vLLM, SGLang, TensorRT-LLM: high-throughput production serving with PagedAttention.
  • GGUF + llama.cpp / Ollama: CPU and consumer-GPU inference.
  • AWQ / GPTQ: quantized formats for fast GPU inference.
  • MLX: Apple Silicon optimized.

13 End-to-End: A Real Fine-Tuning Project

Let's walk through a realistic project: fine-tuning a 7B model to be a SQL-generating assistant.

Step 1 — Define the task

We want a model that, given a natural-language question and a database schema, produces correct SQL. This is a structured output task with clear correctness criteria.

Step 2 — Collect data

  • Start with Spider and BIRD benchmarks (public SQL datasets).
  • Use GPT-4 to generate additional examples from real schemas.
  • Filter: execute each generated SQL against the database; keep only those that run and return correct results.
  • End up with ~8,000 high-quality (schema, question, SQL) triples.

Step 3 — Format as chat

messages = [
  {"role": "system", "content": "You are a SQL expert. Given a schema and question, output only valid SQL."},
  {"role": "user", "content": f"Schema: {schema}\n\nQuestion: {question}"},
  {"role": "assistant", "content": sql}
]
prompt = tokenizer.apply_chat_template(messages, tokenize=False)

Step 4 — Train with QLoRA

from unsloth import FastLanguageModel
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="meta-llama/Llama-3.1-8B",
    load_in_4bit=True
)
model = FastLanguageModel.get_peft_model(model, r=16, alpha=32, target_modules="all")

from trl import SFTTrainer
trainer = SFTTrainer(
    model=model,
    train_dataset=dataset,
    args=TrainingArguments(
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,
        learning_rate=2e-4,
        num_train_epochs=2,
        output_dir="outputs"
    )
)
trainer.train()

Step 5 — Evaluate

  • Run on a held-out test set of 500 examples.
  • Metric: execution accuracy (does the SQL return the right answer?).
  • Also check: does the model still chat reasonably? Run a small general-chat eval.

Step 6 — Iterate

Look at failure cases. Add more examples for schemas the model struggles with. Retrain. Repeat until execution accuracy is acceptable.

Step 7 — Optional preference tuning

If outputs are correct but stylistically poor (too verbose, wrong formatting), collect preference pairs and run DPO for 1 epoch.

Step 8 — Deploy

Merge the LoRA weights into the base, quantize to AWQ-4bit, serve with vLLM.

✦ The Mental Model

Fine-tuning an LLM is a pipeline of progressively more specific training objectives, each building on the last:

  1. Pretraining builds a general-purpose next-token predictor from internet-scale text.
  2. Continued pretraining (optional) injects new knowledge or domains while keeping the same objective.
  3. SFT teaches the model a behavior — to follow instructions, use formats, play a role — via curated input/output pairs.
  4. Preference learning (DPO / RLHF / GRPO) refines the model's outputs against human preferences or verifiable rewards.
  5. Evaluation closes the loop, telling you what to change next.

At every stage, the central trade-off is the same: data quality vs quantity, and expressivity vs efficiency. Modern tools (LoRA, QLoRA, Unsloth) let you do serious work on a single GPU; the bottleneck is no longer compute, it's judgment about data and objectives.

10 Things to Remember

  1. Pretraining teaches language; fine-tuning teaches behavior. Don't conflate them.
  2. Data beats hyperparameters. 1,000 clean examples > 1,000,000 noisy ones.
  3. Always use the model's native chat template. Wrong format = silent garbage.
  4. Default to LoRA or QLoRA. Full fine-tuning is rarely worth the cost anymore.
  5. LoRA has near-zero inference cost. Adapters merge into the base model.
  6. Overfitting is the default failure mode in fine-tuning — use fewer epochs, lower LR, and mixed data.
  7. DPO is the right default for preference learning. Reach for PPO or GRPO when you have a specific reason.
  8. Build a private eval set before you start training. You can't improve what you don't measure.
  9. Catastrophic forgetting is real. Mix in general data and use LoRA to prevent it.
  10. GRPO is the algorithm of the reasoning era. Learn it if you care about math, code, or agents.

✦ Glossary

Adapter

A small set of trainable parameters injected into a frozen model. LoRA adapters are the most common kind.

AWQ

Activation-aware Weight Quantization — a 4-bit quantization method that protects important weights. Great for inference.

Base model

A pretrained model that hasn't been instruction-tuned. It continues text but doesn't follow instructions.

Catastrophic forgetting

When fine-tuning on a narrow task causes the model to lose previously-learned general capabilities.

Chat template

The specific token format a model family uses for multi-turn conversations. Always use the tokenizer's apply_chat_template.

DPO

Direct Preference Optimization — trains a policy directly on preference pairs without a reward model.

GGUF

A quantized model format used by llama.cpp, optimized for CPU and consumer-GPU inference.

GRPO

Group Relative Policy Optimization — an RL algorithm for reasoning models that uses rule-based rewards and no critic.

LoRA

Low-Rank Adaptation — approximates weight updates as the product of two small matrices, enabling efficient fine-tuning.

NF4

NormalFloat 4-bit — a quantization data type designed for normally-distributed neural network weights, used in QLoRA.

PEFT

Parameter-Efficient Fine-Tuning — any method that updates only a small fraction of a model's parameters.

PPO

Proximal Policy Optimization — the RL algorithm used in classical RLHF.

QLoRA

Quantized LoRA — combines 4-bit NF4 quantization of the base model with LoRA adapters trained in BF16.

Rank (r)

In LoRA, the inner dimension of the adapter matrices. Controls the capacity vs efficiency trade-off.

RLHF

Reinforcement Learning from Human Feedback — the original pipeline for aligning LLMs, using PPO and a learned reward model.

SFT

Supervised Fine-Tuning — training on instruction/response pairs to teach a model a specific behavior.

SLM

Small Language Model — typically 1–3B parameters. Easier to fine-tune and deploy than LLMs.
