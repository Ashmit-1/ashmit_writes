Level 1The big picture

An LLM generates text one token at a time. To produce token number 5,000, it must "look back" at all 4,999 tokens that came before it. The question that shapes modern inference engineering is: does it have to redo that work every single time?

The answer is no — and the thing that saves us is the KV cache.

Attention in one paragraph

Inside a transformer, every token produces three vectors: a Query (Q), a Key (K), and a Value (V). To decide how much token A should "pay attention to" token B, the model compares A's Query against B's Key, and uses the resulting weight to blend in B's Value.

Here's the crucial asymmetry: once a token has been generated, its Key and Value never change again. Only its Query changes — and actually, for a token that's already been generated, even its own Query was already used. When we generate a new token, we need its Query, but we need the Keys and Values of everything before it.

So: cache the K's and V's. Never recompute them. That's the whole idea.

Analogy — and where it breaks

The KV cache is like a court stenographer's transcript. Without it, every time a lawyer asks a new question, someone would have to re-interview every previous witness from scratch. With it, you just consult the transcript.

Where the analogy breaks: a transcript is cheap to store. A KV cache is enormous and lives in the fastest, scarcest memory on the GPU. The whole engineering discipline below exists because the "transcript" doesn't fit.

Why the cache is a problem, not just a solution

Suppose a model has h attention heads and a head dimension of d. For every single token in the context, it must store:

KV bytes per token = 2 × h × d × (bytes per number)

              (one for K, one for V)

Now multiply by the number of tokens. Then multiply by the number of users you're serving at once. Then notice that the cache grows during generation, so you can't just pre-allocate it and forget it.

This is why long-context models are hard. Not because the attention math is expensive — because remembering is expensive.

Quick intuition check

A model is serving 8 users at once, each with a 32,000-token conversation. If the KV cache for one conversation is 2 GB, how much GPU memory is the cache consuming?

16 GB. 8 × 2 GB. And that's on top of the model weights. If the model is a 70B-parameter model in 16-bit precision, the weights alone are ~140 GB. This is exactly the arithmetic that motivates every technique on this page.

Level 1Why it matters

The KV cache is not a niche optimisation. It sits at the centre of three commercially important problems:

Serving cost The number of concurrent users a GPU can serve is usually limited by KV cache memory, not by compute. Shrink the cache and you serve more users on the same hardware — a direct cost saving.
Context length A 1M-token context window is only usable if you can afford to store 1M tokens' worth of K and V. Long context and cache efficiency are the same problem wearing different hats.
Decoding speed Token generation is typically memory-bandwidth bound, not compute bound. Every byte of KV cache you must read per step costs time. Fewer bytes → faster tokens.
Fact

During the prefill phase (processing the prompt), the GPU is busy doing arithmetic and is compute-bound. During decode (generating tokens one by one), each step does very little arithmetic but must read the entire KV cache — so it's bandwidth-bound. Almost every KV cache technique is really a bandwidth optimisation in disguise.

Level 2Core concepts: four ways to shrink a cache

Every technique on this page is one of four moves. Learn the four moves and you can place any new paper you read.

Concept 1 — Multi-Head Attention (MHA): the baseline

What it is. The original mechanism from Attention Is All You Need (2017). Each of the h attention heads has its own independent Q, K and V projection.

Why it matters. Independent heads give the model multiple simultaneous "points of view" on the same context — one head might track syntax, another coreference, another positional structure. This is a big part of why transformers work.

The cost. Every head stores its own K and V. The cache is h times larger than a single-head cache would be.

Concept 2 — Multi-Query Attention (MQA): share everything

What it is. Proposed by Noam Shazeer in 2019. All query heads share one single K head and one single V head.

The intuition. Instead of every head keeping its own private notebook of the past, they all read from one shared notebook. The heads still differ — because they still have different Queries, so they ask different questions of the same memory.

The trade-off. Memory drops by roughly a factor of h — dramatic. But the heads lose their independent memories of the past, and published results have repeatedly shown a quality cost. MQA tends to be the most aggressive and the most damaging to quality.

Concept 3 — Grouped-Query Attention (GQA): the practical middle

What it is. Introduced by Ainslie et al. (2023). Query heads are divided into g groups. Each group shares one K head and one V head, but different groups keep separate memories.

The intuition. MQA was too blunt an instrument. GQA asks: what if heads that do similar things share memory, but groups doing different things stay separate? It turns out you can interpolate between MHA (g = h) and MQA (g = 1) and find a sweet spot.

The trade-off. Memory is reduced by a factor of h / g. Quality sits much closer to MHA than MQA does. This is why GQA became the de facto standard in the Llama 2/3, Mistral, and Qwen families, and remains the most common choice in open models today.

Check your understanding

A model has 64 query heads and uses GQA with 8 groups. How many distinct K/V heads are stored, and what's the memory reduction versus MHA?

Reveal answer & reasoning

8 distinct K/V heads; 8× reduction versus MHA.

The number of stored K/V heads equals the number of groups, not the number of query heads. Each group contains 64/8 = 8 query heads, and all 8 of those query heads read from the same K/V pair.

Memory reduction factor = (number of query heads) / (number of groups) = 64/8 = 8×.

Concept 4 — Multi-Head Latent Attention (MLA): compress, don't share

What it is. Introduced in the DeepSeek-V2 paper (2024). Instead of reducing the number of K/V heads, MLA reduces the size of each one.

The intuition. MQA and GQA are like having fewer filing cabinets. MLA is like microfilming the contents: you store a compressed representation, and reconstruct the full K and V only at the moment you need them for attention.

The mechanism, in three steps:

Compress on write When a token is generated, its K and V are projected down into a much smaller latent vector. Only this latent is written to the cache.
Reconstruct on read At each decode step, the latent is projected back up to full K and V dimensions — but only for the tokens actually needed.
Absorb at inference time In the DeepSeek implementation, the up-projection matrices can be algebraically folded into the query and output projections, so decoding avoids an explicit decompression step in the hot path. This is why MLA can be faster, not just smaller.
Fact — and it's counterintuitive

MLA stores roughly the equivalent of 2.25 K/V heads worth of data per token in DeepSeek-V2, versus 8 for an 8-group GQA — yet DeepSeek reported that MLA outperformed MHA on quality in their ablations, not merely approached it. Compression here is not purely lossy in the way quantization is; it's a learned, low-rank reparameterisation, and it can act as a regulariser.

Where it's used. DeepSeek-V2, V3, R1; and adopted in Kimi K2, GLM-5 and other large open models.

Distinguish the moves

For each technique, decide whether it works by sharing or by compressing.

MQA — sharing. One K/V head total.

GQA — sharing. One K/V head per group.

MLA — compressing. Full head count is kept conceptually; the stored vectors are low-dimensional latents.

FP8 / INT4 KV cache — compressing. Same vectors, fewer bits each.

Because sharing and compressing are orthogonal, they stack: DeepSeek uses MLA and FP8 (and in V4.1, FP4) on top of it.

Reveal

By 8×. Going from 8 groups to 1 group is an 8-fold reduction in stored K/V heads.

Notice also that MQA is the theoretical floor for sharing: you can't go below one K/V head. To go further you must compress.

Level 3Paged allocation: solving waste, not size

Everything so far reduces how much cache you need. PagedAttention attacks a different problem: how much of the memory you allocated is actually usable.

The fragmentation problem

In a naive serving system, when a request arrives you reserve a contiguous block of GPU memory sized for the maximum possible output length. Two bad things follow:

  • Internal fragmentation. A request that produces 200 tokens still holds a block sized for 4,000. Most of it is wasted.
  • External fragmentation. Even if you have 10 GB free in total, it may be split into 2 GB chunks that no single request fits into.

Published work on vLLM's PagedAttention reported that naive systems waste the majority of KV cache memory — utilisation figures in the range of 20–40% are commonly cited, versus 90%+ with paging.

The OS analogy — and this one holds up well

Analogy

PagedAttention treats the KV cache exactly like an operating system treats virtual memory. The cache is divided into fixed-size blocks (think: pages). A sequence's K/V data can live in any blocks, anywhere in GPU memory. The system keeps a block table per sequence mapping logical positions to physical blocks — just like a page table.

Where it holds up: the mechanism genuinely is the same idea, and the implementation borrows the terminology deliberately.

Where it differs: there's no disk to swap to. Everything lives in GPU memory. And blocks can be shared between sequences — for example, many conversations starting with the same system prompt can share those prefix blocks, with copy-on-write if they diverge.

What paging buys you

Near-elimination of internal fragmentation You allocate blocks as they're actually needed, not up front for a worst case.
No external fragmentation Any free block fits any sequence. There's no "large enough contiguous region" requirement.
Prefix sharing Multiple requests with a common prefix (system prompts, few-shot examples) share the same physical blocks. A large real-world win in chat and RAG serving.
Enables eviction and offloading Because blocks are discrete and indexed, you can move them to CPU memory or evict them as a unit. PagedEviction (2026) extends this with structured block-wise pruning.
Be precise about what it doesn't do

PagedAttention does not reduce the theoretical size of the KV cache. If your model produces 2 GB of cache, it produces 2 GB of cache. What paging changes is how much of your GPU's memory budget goes to useful cache versus wasted gaps. It's a utilisation technique, not a compression technique — and it composes with all the compression techniques.

Level 3Quantized caches: fewer bits per number

Instead of storing K and V as 16-bit floats, store them as 8-bit or 4-bit values. Same structure, half or a quarter of the bytes.

Why this is not free. Attention scores are computed by comparing Q against K. If K has been rounded, the comparison is slightly wrong. Crucially, errors in K propagate into the attention weights, which then reweight all the values — so the effect isn't a simple "small noise added to the output."

Why K and V are quantized differently

Keys and Values have measurably different distributions:

  • Keys contain outlier channels — a small number of dimensions with values far larger than the rest. Naively quantizing with a single scale factor destroys the small values. The standard fix is per-channel scaling for keys, or isolating the outlier channels and keeping them in higher precision.
  • Values are more uniform, so per-token scaling works better for V.

Research systems like KIVI and KVQuant exploit exactly this asymmetry. Production runtimes (vLLM, TensorRT-LLM, SGLang) have converged on FP8 (E4M3) as the practical default because it has hardware support on Hopper-and-later GPUs and needs no calibration.

Uncertainty — read this before trusting a number

Quality impacts of quantization are highly task dependent. A model with an FP8 KV cache may show no measurable degradation on conversational benchmarks and a clear degradation on a needle-in-a-haystack retrieval task. Any single "X% quality loss" figure you see should be treated as applying to the specific benchmark it was measured on. Always re-evaluate on your workload.

Reason it out

You have a model using MLA and you want to reduce KV cache memory further. Should you switch to a more aggressive GQA configuration, or add FP8 quantization?

Reveal a reasonable answer

Add FP8 quantization. The model was trained with MLA. Changing the attention structure at inference time isn't something you can just do — GQA groups aren't a runtime knob, they're baked into the trained weights. Switching would require retraining.

Quantization, by contrast, is largely a runtime decision. You can apply FP8 to the cache of an existing checkpoint and evaluate whether quality holds.

This is a general principle: architectural choices are locked at training time; precision choices are (mostly) made at serving time. Knowing which bucket a technique falls into tells you who can actually use it.

Level 3How it evolved

Each step was a response to a specific limitation of the previous one. Follow the chain of reasoning, not just the dates.

2017
MHA — Multi-Head Attention
The original transformer. Maximum representational richness, maximum memory cost. Fine for research-scale sequences; untenable at serving scale.
2019
MQA — Multi-Query Attention
Shazeer's insight: the K/V cache, not the compute, is what limits batch size. Collapse all heads to one shared K/V. Huge memory win, real quality cost. Problem it created: quality loss made people reluctant to adopt it for flagship models.
2023
GQA — Grouped-Query Attention
Ainslie et al. showed you can uptrain an existing MHA checkpoint into GQA, recovering most of the quality at a fraction of the memory. Why it won: it's a smooth dial, not a cliff. Became standard in Llama 2/3, Mistral, Qwen.
2023
PagedAttention (vLLM)
Kwon et al. attacked a different axis: memory utilisation. A serving-system contribution rather than a model-architecture one, which is why it composes with everything else.
2024
MLA — Multi-Head Latent Attention
DeepSeek-V2. Instead of sharing heads, compress them. Reported to beat MHA on quality at GQA-like memory cost. Broke the assumption that cache reduction must cost quality. Cost: architectural complexity and kernel work.
2024–25
Quantized KV caches reach production
FP8 KV cache becomes a checkbox in vLLM, TensorRT-LLM and SGLang. Another 2×, largely free, on top of whatever architectural choice you made.
2026
DeepSeek V4.1 Flash
Stacks everything: sparse attention, FP4, bounded replay, and a new compressed sparse attention variant. Reports ~4× reduction versus V4-Flash and ~437× versus V1. See the caveat section below.
The pattern

The field moved from sharing (cheap, effective, quality-limited) to compressing (more complex, quality-preserving) to stacking (combine everything). Each generation didn't replace the last — it added another multiplicative factor. GQA is still the right answer for many models; MLA is the right answer when you can afford the training complexity; quantization applies regardless.

The named components, and what each one is actually doing

Compressed Sparse Attention 2 (CSA-2) An evolution of the MLA lineage with sparsity layered in. The name suggests two things happening at once: the compression of MLA (store latents, not full K/V) and sparsity (not every cached position is attended to at every step). Uncertainty: the precise sparsity pattern and selection criterion aren't fully specified in the public material I could verify.
NSA-style sparse MLA Native Sparse Attention combined with MLA. Sparse attention reduces compute; MLA reduces memory. These are orthogonal bottlenecks, which is why combining them makes sense — but it also means the engineering complexity compounds.
FP4 KV cache Four bits per value, versus FP8 in V3.2. This is a further 2× on top of MLA's compression. FP4 for KV cache is genuinely aggressive — the quality implications at 1M context are not yet well characterised in the public literature.
SWA Bounded Replay Sliding-Window Attention with selective recomputation. Rather than storing every intermediate state forever, the system discards some and recomputes the small portions it needs later. This trades compute for memory — a classic and sound trade when you're bandwidth-bound and have spare FLOPs, but it makes latency less predictable.
Causal encoder–decoder asymmetry Input processing activates ~80B parameters; output generation activates ~160B. This is a prefill/decode asymmetry — cheaper to read a prompt than to generate from it. It targets prefill cost specifically, which is a different axis from KV cache size.

Interpretation — my read, clearly labelled as such

V4.1 Flash is best understood not as a single invention but as an aggressive stacking of techniques that were individually already known. The genuinely novel parts appear to be (a) making FP4 viable for KV cache at 1M context, and (b) the recompute-instead-of-store trade in SWA Bounded Replay.

That stacking has a cost that doesn't show up in the memory figures: a serving stack that must simultaneously implement sparse attention selection, latent decompression, FP4 kernels, and bounded replay is far harder to debug, profile, and port to new hardware than a GQA model with an FP8 cache. If you're choosing a strategy for a product, "what's the simplest thing that fits my memory budget" is usually the right question — not "what's the smallest possible cache."

Think critically

The reported figure is "437× reduction versus V1." V1 used a different, older architecture entirely. Is that a fair comparison?

Reveal a discussion

It's a fair historical comparison and a misleading competitive one.

As a statement about how far the field has come across several architecture generations, 437× is a legitimate and striking summary. It's the kind of number that's meaningful when you plot the trend over years.

But if you're deciding what to deploy today, the relevant comparison is against the current alternative — a GQA or MLA model with an FP8 cache — not against a 2024-era baseline. The 4× figure versus V4-Flash is the more decision-relevant number, and it's much less dramatic.

This is a general habit worth building: when you see a big multiplier, check what the baseline is and whether that baseline is something anyone would actually choose today.

Level 5Deeper dive: the trade-off triangle

Every technique on this page moves you around a three-way trade. You cannot optimise all three at once.

Read the triangle like this: a technique that pushes you toward one vertex necessarily pulls you away from the opposite edge.

  • MQA buys memory and speed at a real quality cost. It sits nearest the MEMORY–SPEED edge.
  • GQA sits comfortably in the middle. That's why it won: it doesn't excel at anything but it doesn't hurt anything much either.
  • MLA is unusual because it moves toward the MEMORY vertex without moving away from QUALITY. This is the closest thing to a free lunch in the field — but you pay in architectural complexity and the need for custom kernels.
  • Quantization is a small, cheap step in the memory direction with a small quality cost. It stacks on everything.
  • Paging sits off the triangle entirely — it improves utilisation without moving you along any edge.

Nuances worth knowing

Compression ratio isn't constant across layers

Not all layers need the same amount of KV precision. Some layers are highly sensitive to cache errors; others tolerate aggressive compression with no measurable effect. Research on layer-wise and head-wise mixed-precision caching exploits this, but it adds tuning burden that most teams don't take on.

The decode bottleneck is bandwidth, not capacity

This distinction matters more than it first appears. If you're bandwidth-bound, a smaller cache helps even if it fits in memory already — because you read less per token. If you're capacity-bound (too many users), a smaller cache lets you serve more users. The same technique helps in both cases but for different reasons, and the correct optimization depends on which regime you're in.

KV cache and training are linked

You can't retrofit GQA onto an MHA model at inference time — the weights have to be trained or uptrained. MLA likewise must be trained in. This is why architecture choices have long half-lives: once a model family commits, it's committed for that generation.

Long-context evaluation is harder than it looks

A model can look fine on a 4K-token benchmark and fail badly at 128K with the same compression. The standard failure mode is losing the ability to retrieve a specific fact from deep in the context. If you care about long context, benchmark at the length you actually need.

Application exercise

Scenario

You're deploying a 70B open-weights model for a document-QA product. Users paste ~50,000-token documents and ask questions. You need to serve at least 8 concurrent users on a single 80 GB GPU. The model ships with GQA using 8 groups, 64 query heads, head dim 128, BF16.

Question: What's the first thing you'd try, and what would you measure?

Reveal a worked answer

First, do the arithmetic. KV per token = 2 (K and V) × 8 heads × 128 dim × 2 bytes = 4,096 bytes ≈ 4 KB. For 50,000 tokens: ~200 MB per sequence. For 8 users: ~1.6 GB. That's small relative to 80 GB.

So the cache is not your bottleneck. The model weights are: a 70B model in BF16 is ~140 GB, which doesn't fit on one 80 GB GPU at all. You'd need quantization of the weights (4-bit gets you to ~35 GB) before KV cache is even a consideration.

What I'd actually do: quantize the weights to 4-bit, use paged KV cache to avoid waste, and measure quality on the document-QA task specifically — because 4-bit weight quantization plus long-context retrieval is exactly the combination where degradation shows up.

What I'd measure: not perplexity. Perplexity is insensitive to the failure mode that matters here. I'd measure answer accuracy on questions whose answers are buried at varying depths in the 50K context, at several positions, and compare against the unquantized model.

The meta-lesson: do the arithmetic before reaching for a technique. The most sophisticated KV cache method in the world won't help if your cache is 2% of your memory budget.

SynthesisThe mental model

If you remember nothing else from this page, remember this framework.

The one-paragraph version

A transformer generating text must look back at every previous token. Recomputing those lookups every step is wasteful, so we cache the Key and Value vectors. That cache grows linearly with context length and concurrency, and it — not compute — is what limits how many users you can serve and how long a context you can afford. Every technique in the field is one of four moves: share fewer K/V heads (MQA, GQA), compress what you store (MLA, quantization), organise it without waste (paging), or discard parts of it (sparsity, eviction, recomputation). These moves are orthogonal and stack multiplicatively. The field's trajectory has been from sharing (cheap but quality-limited) to compressing (complex but quality-preserving) to stacking everything at once — with DeepSeek V4.1 Flash as the current extreme, combining MLA-lineage compression, FP4 precision, sparsity, and selective recomputation.

5–10 things to remember

  1. The KV cache exists because K and V for a generated token never change — only the new token's Q does. Caching them removes redundant work.
  2. The cache is the bottleneck for long context and high concurrency, and decoding is bandwidth-bound, not compute-bound. Almost every technique is really a bandwidth optimisation.
  3. There are exactly four moves: share, compress, organise, discard. Place any new paper into one of these and you'll understand it faster.
  4. MQA shares one K/V across all heads — maximum memory win, real quality cost. GQA shares within groups — the pragmatic default in most open models.
  5. MLA compresses rather than shares, and reported quality can exceed MHA while using far less memory. It's the closest thing to a free lunch in the field, paid for in architectural complexity.
  6. PagedAttention reduces waste, not size. It's an OS-style memory manager for the cache and composes with everything else.
  7. Quantization stacks on top of architectural choices and is mostly a serving-time decision, unlike GQA/MLA which are locked in at training time. FP8 is the production default; FP4 is the frontier.
  8. Quality impact is task-dependent. Any single "X% degradation" figure applies to the benchmark it was measured on. Always re-evaluate on your own workload at your own context length.
  9. DeepSeek V4.1 Flash stacks compression, FP4, sparsity and recomputation for ~4× reduction versus V4-Flash. Treat the headline numbers as vendor-reported pending independent verification, and remember that complexity itself is a cost.
  10. Do the arithmetic first. The most sophisticated cache technique is worthless if your cache is 2% of your memory budget and your weights are 98%.

The phase where the model generates tokens one at a time. Memory-bandwidth bound — little arithmetic, but the whole KV cache must be read each step.
MHA — Multi-Head Attention
The original mechanism: each attention head has its own independent Q, K and V projections. Baseline memory cost.
MQA — Multi-Query Attention
All query heads share a single K and V head. Maximum sharing-based reduction; measurable quality cost.
GQA — Grouped-Query Attention
Query heads are divided into groups; each group shares one K and V head. Interpolates between MHA and MQA. The current production default.
MLA — Multi-Head Latent Attention
K and V are projected into a low-dimensional latent space for storage and reconstructed for attention. Compression rather than sharing. Introduced by DeepSeek-V2.
PagedAttention
Memory management for the KV cache using fixed-size blocks and per-sequence block tables, eliminating fragmentation. Introduced by the vLLM team.
KV Cache Quantization
Storing cache values in lower precision (FP8, INT8, INT4/FP4) to reduce bytes per value. Lossy but often cheap.
Sparse Attention
Attending to only a subset of positions rather than all of them. Reduces compute, which is a different bottleneck from cache memory.
Fragmentation
Wasted memory caused by allocation patterns — gaps too small to be useful, or space reserved for a worst case that never materialises.
MoE — Mixture of Experts
An architecture where only a subset of parameters is activated per token, reducing compute per token at the cost of higher total memory.
HBM — High-Bandwidth Memory
The fast memory attached to a GPU, where weights and KV cache live. Its bandwidth is often the limiting factor during decoding.

ReferenceSources & further reading

Honest note on sourcing

I was not able to retrieve and verify full citation metadata for every item below during the preparation of this page. The foundational papers (MHA, MQA, GQA, MLA, PagedAttention) are well-established and I'm confident in their attribution. The DeepSeek V4.1 Flash material is recent and vendor-reported. Where I've given a general pointer rather than a precise citation, that reflects genuine uncertainty rather than laziness — please verify anything you intend to rely on.

Foundational papers

Vaswani, A. et al. (2017). Attention Is All You Need. NeurIPS. — The original transformer and MHA.

Shazeer, N. (2019). Fast Transformer Decoding: One Write-Head is All You Need. arXiv:1911.02150. — Introduced MQA.

Ainslie, J. et al. (2023). GQA: Training Generalized Multi-Query Transformer Models from Multi-Head Checkpoints. arXiv:2305.13245. — Introduced GQA and the uptraining recipe.

Kwon, W. et al. (2023). Efficient Memory Management for Large Language Model Serving with PagedAttention. SOSP. — Introduced PagedAttention and vLLM.

DeepSeek-AI (2024). DeepSeek-V2: A Strong, Economical, and Efficient Mixture-of-Experts Language Model. — Introduced MLA.

KV cache optimization surveys

Towards Efficient Large Language Model Serving: A Survey on System-Aware KV Cache Optimization. ACL Findings, 2026. — Broad survey covering sharing, compression, paging and eviction.

A Survey on Optimization Techniques for On-Device Large Language Model Inference. IEEE, 2026. — Includes KV cache optimization and quantization in the on-device setting.

Quantization

Liu, Z. et al. KIVI: A Tuning-Free Asymmetric 2bit Quantization for KV Cache. — Exploits the per-channel structure of K versus the per-token structure of V.

Hooper, C. et al. KVQuant: Towards 10 Million Context Length LLM Inference with KV Cache Quantization. — Aggressive KV quantization with outlier handling.

vLLM documentation — FP8 KV cache and quantization support. Practical guidance on production FP8 cache configuration.

DeepSeek V4.1 Flash

DeepSeek V4.1-Flash Technical Report (September 2026). — The primary source for the KV cache reduction figures and the named architectural components (Compressed Sparse Attention 2, SWA Bounded Replay, FP4 cache). Vendor-published; independent verification limited at the time of writing.

DeepSeek-V3.2 / FlashMLA FP8 documentation. — Details of the FP8 decoding kernel that V4.1's FP4 work builds on.

DeepSeek V4 sparse MLA backend documentation (as implemented in vLLM and SGLang). — Implementation-level detail on sparse MLA serving.

Eviction and sparsity

PagedEviction: Structured Block-wise KV Cache Pruning. EACL Findings, 2026. — Extends paging with structured block-level eviction.

Xiao, G. et al. Efficient Streaming Language Models with Attention Sinks. — StreamingLLM; the origin of the observation that a few initial tokens act as attention sinks and must be retained.

Accessible explanations

Raschka, S. Multi-Head Latent Attention (MLA) and accompanying transformer architecture writing. — A clear technical walkthrough of MLA's mechanism and adoption; useful as a second explanation of the compression idea.
